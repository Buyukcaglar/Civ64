## 0. Conventions

### 0.1 Classes (prompt 5.4)

| Class | Meaning in this file |
|---|---|
| **N** | DOS-native scene: the whole frame is the N canvas, drawn as the DOS program draws that screen; the core's events drive it |
| **R** | re-skinned Windows UI element: rendered from the `w16` control tree in the DOS popup style (DOS font, frame, colours, layout rules); input mapped to the Windows controls. Over an N scene it is drawn on the N canvas; during play (A canvas) it stays at the Windows position (prompt 5.3) |
| **A** | art substitution in the Windows layout: the map, small-map and status windows during play |
| **W** | no DOS counterpart: shown exactly as in the Windows profile; the reason is given (section 4); over an N scene see 4.1 "W over N" |
| **open** | the drafts do not decide the class; none remain after review R3 (1.8) |

### 0.2 Timeline codes (prompt 5.5)

| Code | Meaning |
|---|---|
| **TD** | DOS native timeline: T1 (starts when the core starts the Windows sequence), T2 (both timelines advance; a switch shows the other one at the same virtual time), T4 (a DOS sequence that ends first shows the next known screen or holds its last frame), T5 (a skip ends every profile's sequence), T6 (virtual clock) |
| **TC** | the core's timing (T3, T7): the scene opens, steps and closes on the core's events; game-logic animations (unit moves, combat, map cycling, city animations) keep the core's pace |
| **TX** | a DOS-only effect inside a scene, on the DOS timing of the DOS listing (T7, last sentence): fades, palette cycling, strip reveals, `G#10` dissolves |
| **TS** | static: redrawn from the core's drawing events, no timing of its own |

A row may combine codes, for example "TS + TX" for a static scene with a DOS fade-in.

### 0.3 Adapters (prompt 5.6 I3)

Every interactive N or R element names an adapter. The proposals are in section 1.7. Names:
I-intro, I-title, I-birth, I-setup, I-custom, I-text, I-menu, I-stack, I-wait, I-city, I-report,
I-pedia, I-palace, I-space, I-play, I-menubar, I-pass (all input passes unchanged, I2), I-none (no input
is expected; input passes to the core unchanged).

### 0.4 Labels and confidence

| Label | Meaning |
|---|---|
| **proved** | a shared table, string or constant ties the DOS source to the Windows item (named in the row) |
| **inferred** | role, call structure, order, equal counts or a scaled numeric match (×1.6 logical to device, ×2 sprite sheet, ×1.33 in x for 427-wide pictures) |
| **DOS file**, **DOS listing** | the label of the draft that states the DOS fact |
| **unknown** / **open** | not decided by the drafts; listed in the Open section |

Confidence (high, medium, low) applies to the proposed source or rule, not to the DOS fact.

### 0.5 "Never substituted"

WI 8 lists the pictures and shapes whose pixels or palette the core reads back as data. They are
marked **never substituted** in section 2.1. The core always loads and reads the Windows
picture; the DOS profile never changes emulated memory (prompt 8, O4). Where such a picture is
also displayed, the DOS renderer may show DOS art in its own shadow surface, but every result
the core derives from the Windows pixels (positions from opaque bounds, star placement, nearest
colour tables, key colours, the EARTH terrain) is taken from the core, never recomputed from DOS
art. Picture 137 is never displayed in either profile.

### 0.6 Rules that apply to many rows

1. **Core decisions.** Where the core decides something that the DOS program also decides, the
   DOS renderer follows the core (prompt 5.4). Cases found: the map redraw order (core
   DrawTilesToPort mode 1 with RandomBelow; DOS `random(256)` then `p = 5p + 1`,
   SCENES-PLAY 2.4), the active-unit blink phase (core 1 s cycle; DOS 20 frames,
   SCENES-PLAY 6.1), the leader's idle animation (core timer with `RandomBelow(2)`; DOS every
   10 frames, SCENES-PLAY 7.9), the newspaper's name form, tag and slogan (core `RandomBelow(4)`,
   `(2)`, `(14)` at 1138:03C2, 04A1, 058B; DOS four forms, two tags, sections NEWSA..NEWSN,
   SCENES-PLAY 7.7), the starfield (core star positions; DOS 20 stars on black,
   SCENES-PLAY 7.16), the city disaster case (core; DOS one of 10, SCENES-PLAY 7.6). The
   resolution of SCENES-PLAY Open 7: the DOS dissolve order is not used, so the C library's
   `rand` state is never involved.
2. **Presentation-local generators.** A DOS-only effect with no core decision behind it uses the
   DOS algorithm with a presentation-local generator seeded deterministically, never
   `g_randSeed` (prompt 5.4). Candidates: `G#10` DissolveToScreen (an LFSR without `rand`,
   DRIVER 4, TIMING 3.7, so deterministic already), the newspaper's torn edge (DOS
   `random(2)` per piece, SCENES-PLAY 7.7; the core's edge draws `RandomBelow(3)` and `(13)` per
   segment at 1138:01B8..01C8 and has another shape), the ornamental border tile choice
   (R:0866:260E through R:1DC4:005D, SCENES Open 8), the city view layout (a D1 decision: OPEN P20; Open 21).
3. **Interface colours** come from the palette in effect in each DOS scene, not from a fixed EGA
   table (PALETTE 6, **inferred** there): grey 7 differs between Birth, the title and play.
4. **Text.** Static text of N and R elements comes from the DOS program where the DOS screen has
   the same element; dynamic text (names, numbers, messages the game logic generates) comes from
   the core (prompt 5.4). Sources: section 3.4. The DOS game writes index caches into its
   section files (FORMATS 3.3 step 6, Open 3); the port reads the DOS directory only and never
   writes or creates a DOS file (prompt 5.9).
5. **Sound** is the core's `.wav` calls in both profiles (prompt 5.9); DOS sound is out of scope.
6. **Pointer.** The DOS pointer is the `TORCH.PIC` sprite with hot spot (0, 0), drawn with the
   current palette (FORMATS 4; PALETTE 5). The DOS program hides it during the intro, Birth and
   while scenes draw (SCENES 7.1, 7.3; SCENES-PLAY 0.1). In play only two shapes are
   used, the torch D4CE[7] and the GO arrow D4CE[2] (DOS listing; reviews R2-1 and F2;
   SCENES-PLAY Open 3). The case 67h (`g`) of the order switch R:0403:1AED runs
   R:0403:0FFD..10B8 once per dispatch. With the mouse active (DGROUP:1A3C ≠ 0), R:0000:1697 at
   R:0403:10AB sets the GO arrow while a local flag is clear and the torch while it is set;
   the xor at R:0403:10B3 then toggles the flag. So the first `g` shows the arrow and a second
   `g` restores the torch. A map click while the flag is set stores the square in the unit
   record bytes DGROUP:81DA/81DB (+ 600h·civ + 0Ch·unit, and FFh into 81DC) when the unit's
   domain allows it, then clears the flag and restores the torch (R:0403:09D9..0AEC);
   R:0403:0456..046B and 094A..095B also clear it and restore the torch. Without a mouse the
   case starts or ends a keyboard square selection (R:0403:1007..1088), not a blink. Bytes
   81DA/81DB are +6/+7 of a 12-byte record with a stride of 600h per civilization, the offsets
   of the Windows Unit.gotoX/gotoY (claude/src civ_structs.h), so the case is read as the GoTo
   order (inferred). No other DOS pointer shape was found.
7. **Mouse (I5).** In N scenes a DOS point L maps to a device point d of the window the core
   uses, chosen so that the core's own conversion maps d back to L. Four conversion classes
   occur (showfunc):
   * **PollMouseClick** 1108:0000 stores the click as signed `lParam*10/16` (idiv at
     1108:0169..018F): d = ⌈16L/10⌉. Callers: ShowIntelligenceAdvisor 1018:1641 (INFO buttons),
     ShowSpaceshipArrival 11D8:07DB, PlayReplay 1180:0DC8, BlinkActiveUnitUntilInput 11C0:11A2,
     WaitTicksOrInput 11D8:0BFC. It keeps other windows' clicks by window, which matters only
     in A.
   * **WaitForKeyOrClick** 1038:0C1D stores `lParam*10 >> 4` unsigned (1038:0CB6..0CDA): the
     same d = ⌈16L/10⌉ for the non-negative points of a 512x320 dialog. CityScreenWndProc
     1030:9C17 uses the same unsigned `*10 >> 4` for g_mouseX/Y (1030:9CD0..9D3B).
   * **Control rectangle.** `w16` child controls hit-test in device pixels: MenuZ 1220:0156
     creates its options as `RanDoMRadio` child windows (CreateWindow at 1220:08D5 and
     1220:09B0, ids 500 + i); the Region controls of dialog 143; EDIT controls; list boxes; the
     owner-drawn city buttons 96h..98h; OK, Cancel and Go Back buttons. A click is translated to
     a device point inside the control's rectangle in the `w16` tree; no logical conversion is
     involved.
   * **ScaleLogical forward**: hit rectangles that the core scales with ScaleLogicalX/Y need
     d = ScaleLogical(L).

   The class of each adapter is in 1.7.1. D1 proves each class per scene (OPEN.md P15).
8. **Characters (prompt 5.10).** Every DOS font ends at code 7Fh or lower (FORMATS 2.2: fonts 4,
   5 and 9 end at 7Ah, 7Dh and 7Eh), and the DOS text routine G#21 treats every byte of 80h and
   above as a colour change to `byte & 7Fh` (FORMATS 2.3, G:0000:0F9C); codes outside a font's
   first..last range are skipped without advance. DOS name entry accepts only 20h..7Fh
   (SCENES 10.4). The DOS program has no substitution of its own. Rule proposed for D1 (OPEN.md
   P13): colour bytes are honoured only in DOS-sourced static text (P5); a core byte of 80h and
   above, or below 20h, is shown by one recorded substitution (for example a fixed fold to 7-bit
   letters, or a placeholder glyph); name entry accepts whatever the core accepts (prompt 5.10).
